## Objective (as accepted)

Prove Voting as a genuinely different Interaction Engine — not a reskinned Multiple Choice — via the smallest correct implementation: host-authored or Open-Response-derived Candidates → Voting → derived `placement` → reveal. Validate Candidate Resolution (including across an Interaction Instance boundary), Voting-owned immutable Candidate snapshots, participant vote persistence and revision, authoritative closing, ties, lifecycle integration, passive synchronization, host/participant rendering, and non-interference with Open Response and Multiple Choice. Image/media Candidates, media moderation, ranked-choice voting, persistent progression, Gameplay Scoring Taxonomy, URBANO rewards integration, and Experience Composition redesign are explicitly out of scope.

Grounded in the committed Product architecture (`Gameplay_Outcome_Taxonomy.md`, `Interaction_Engine_Taxonomy.md`, `Interaction_Instance.md`, `Game_Composition_Architecture.md`, `Interaction_Modifiers.md` — `433b61e`) and in the actual `urbano-gaming` repository's existing patterns (Open Response / Multiple Choice, `ENGINEERING_PATTERNS.md`, migrations 0009–0029).

## Design Decisions Incorporated (from the architecture and software-design review)

- **`EngineType`** gains `"VOTING"` as a third member.
- **Candidate representation**: `label: string` only — this slice's text-only presentation field, explicitly not a claim about a future non-text Candidate architecture. No generalized Candidate payload abstraction.
- **Structured-domain-input → SQL mapping**: `VotingCandidateSource` (`{ type: "HOST_AUTHORED", candidates }` | `{ type: "SUBMISSION", sourceInteractionInstanceId }`) is one coherent, mutually-exclusive-by-construction TypeScript union all the way through the domain layer and the `SessionRepository` interface. Decomposition into flat SQL parameters (`p_voting_source_type`, `p_voting_candidates` jsonb, `p_voting_source_interaction_instance_id`) happens exactly once, inside `SupabaseSessionRepository.startSession` — the one boundary where Postgres's lack of a native discriminated-union type actually forces a shape change. `InMemorySessionRepository` needs no such decomposition at all, since it's plain TypeScript.
- **Candidate Resolution owner**: inside `start_session_atomically`, the same atomic operation that already resolves prepared-question content into a new Interaction Instance (0026) — no new orchestration layer.
- **`placement` persistence**: **not persisted.** Derived live via `computeVotingResults` (standard competition ranking, native to a plain sort — no SQL `rank()` needed since both repository implementations compute it in TypeScript for identical semantics) from immutable `votes` + `voting_candidates` rows, called only once the interaction reaches `RESULT_REVEAL`. Mirrors Multiple Choice's own `correctness`, which is derived at `GET_SESSION` read time and never stored. Consequence: **no `voting_placements` table, no Voting branch in `reveal_results_atomically`** — five migrations, not seven.
- **Vote persistence**: a new `votes` table (not a reuse of `submissions`, unlike Multiple Choice) — a deliberate divergence, justified by real referential integrity (`candidate_id` as a genuine foreign key) and by the committed Outcome Taxonomy's own conclusion that a cast vote is conceptually distinct from a submission.
- **One vote per participant**, revisable via upsert while `PROMPT_ACTIVE` (mirrors `submitResponse`'s existing last-write-wins shape exactly — reusing it costs nothing extra), immutable once not `PROMPT_ACTIVE`. No self-vote restriction (the chosen proving case doesn't require one).

## Data Model

```
voting_candidates(candidate_id, interaction_instance_id, ordinal, label, created_at)
votes(vote_id, interaction_instance_id, participant_id, candidate_id, created_at, updated_at)
```
No `voting_placements` table — see above.

## Candidate Resolution Implementation

Inside `start_session_atomically` / `InMemorySessionRepository.startSession`, keyed on `votingCandidateSource`:
- `HOST_AUTHORED`: validates ≥2 distinct, non-empty (post-trim) candidates (fast-path in `startSession.ts`, re-enforced authoritatively in the atomic function/repository), inserts one `voting_candidates` row per candidate, ordinal-ordered as supplied.
- `SUBMISSION`: re-verifies the named interaction instance belongs to this session, is `OPEN_RESPONSE`, is `RESULT_REVEAL`, and has ≥1 submission, then copies each submission's `text` into a new `voting_candidates` row, ordinal-ordered by submission `created_at`. The source interaction instance is never written to — confirmed directly in the operational simulation (step 6: source's own `getSubmissionsForInteractionInstance` still returns its original 2 rows after Voting starts).

Both paths run inside the exact same atomic operation as the new interaction instance's own creation.

## Defects Discovered and Corrected During Implementation

- **Test-writing error, caught before running**: an early draft of a "rejects a source interaction that has not been revealed yet" test asserted the wrong exception. Tracing the actual call graph showed this system's existing "the previous interaction must already be `RESULT_REVEAL`" precondition (which guards *every* `START_SESSION` call, not just Voting's) always fires first for the only interaction a not-yet-revealed `SUBMISSION` source could ever name — the current interaction itself, since every earlier interaction is guaranteed already revealed by induction. Corrected the test to assert `PreviousInteractionNotRevealedError`, and confirmed by inspection that `VotingSourceInteractionNotEligibleError`'s specific "not `RESULT_REVEAL`" branch is, as a consequence, unreachable through any real call path in this system today. Kept as defense-in-depth (a genuine, if currently unreachable, guard against a future change — e.g. parallel interaction instances — that could make it reachable) rather than removed, and not asserted by a test, since no real call path exercises it.
- **Test scaffolding cleanup**: an early draft of the tie/ranking tests accumulated dead placeholder code from iterative writing (an unused helper, a broken double-call in the vote-revision test). Rewritten cleanly before the suite was run — caught during self-review, not by a failing test.

## Defects Found and Fixed During Pre-Commit Review

- **Missing schema-level Candidate/interaction-instance integrity** (`0031`/`0032`). `votes.candidate_id` was a bare foreign key to `voting_candidates(candidate_id)` — the schema alone could not prevent a vote from referencing a Candidate belonging to a *different* Voting interaction instance than the vote's own `interaction_instance_id`; only `cast_vote_atomically`'s explicit application-level check enforced that. Fixed by adding `voting_candidates_instance_candidate_unique` (a composite unique constraint on `(interaction_instance_id, candidate_id)`, alongside the existing primary key) and changing `votes.candidate_id` to a composite foreign key `(interaction_instance_id, candidate_id) references voting_candidates (interaction_instance_id, candidate_id)`. The application-level check in `cast_vote_atomically` is retained (it produces a clean `InvalidCandidateSelectionError` instead of a raw FK-violation error) — the schema change is defense-in-depth, not a replacement. Both migration files were edited in place, not patched with new migrations, since neither has been applied anywhere yet.
- **Ambiguous `START_SESSION` combination not rejected**. Supplying both `preparedQuestionId` and `votingCandidateSource` on the same call silently let `preparedQuestionId` win (mirroring `promptText`'s existing "ignored when a prepared question is named" precedent) rather than being rejected — a real gap, since silently dropping an entire alternate engine selection is a much larger silent failure mode than ignoring a redundant text field. Fixed with a new `AmbiguousStartSessionTargetError`, thrown by `startSession.ts` (fast path) and re-enforced authoritatively in both `start_session_atomically` (0033) and `InMemorySessionRepository.startSession`, mapped to a 400 at the API route.
- Both fixes are covered by new tests (see Tests, above) and do not change scope, migration count, or any previously-reported design decision.

## SESSION_COMPLETE Behavior — Precise Resolution

The implementation record originally described this as a vague "corner-cut." Resolved precisely:

- **Underlying data**: never lost. `votes`/`voting_candidates` rows are permanent; `GET_SESSION` simply stops surfacing `votingResults` once `session.state` is `SESSION_COMPLETE` (its gating condition requires `session.state === "LOBBY_LOCKED"`), exactly mirroring `submissions`'s own pre-existing, already-accepted behavior — not a Voting-specific gap.
- **Host**: `host.html` has no completion-screen override function — `renderResults`'s `lastKnownSubmissions` client-side cache is the *only* thing keeping `resultsCard` visible after `SESSION_COMPLETE` today. `renderVotingResults` did not have the equivalent cache, so `votingResultsCard` really did vanish a turn earlier than `resultsCard` would have for the same host, in the same situation. **This was a real, user-visible asymmetry — fixed** by adding an identical `lastKnownVotingResults` cache to `host.html`, reset at the same two points `lastKnownSubmissions` is (interaction change, new session).
- **Participant**: `participant.html` behaves differently by design — `updateCompletionScreen()` (Structural Tier 2) unconditionally hides `resultsCard` (and, from this slice's original implementation, `votingCard`/`votingResultsCard` too) once `SESSION_COMPLETE` is reached, replacing the last Turn entirely with a dedicated completion screen (standings/winner only). Voting already matched this real behavior from the first implementation pass — **no fix was needed on the participant side**; the initial "corner-cut" note conflated host and participant behavior, which are not actually the same mechanism.
- **Standings, winner banner, rematch/continuity**: entirely unaffected in both cases — all three are computed independently of Voting (standings from `point_awards`, which Voting never writes to in this slice; successor fields from their own, separate lookup).
- **Trigger for revisiting further**: none needed — host and participant now both match their respective engines' existing, established behavior exactly. If a future slice changes how `submissions`/`resultsCard` behaves at `SESSION_COMPLETE` (e.g. persisting across reloads, not just page loads), `votingResults`/`votingResultsCard` should change the same way, at the same time, not independently.

**One real, general infrastructure finding, unrelated to Voting**: a fresh `supabase start` database does **not** replicate a cloud project's default `service_role`/`anon`/`authenticated` grants — confirmed by checking `sessions` (migrated in `0001`, untouched by this slice) and finding it had the identical restricted grant set. **RLS and authorization**: queried `pg_class.relrowsecurity` for every table in `public` — **RLS is disabled on all eleven tables, `voting_candidates` and `votes` included**, with no exception. Cross-checked grants and function security on `voting_candidates`/`votes`/`cast_vote_atomically` against `submissions`/`multiple_choice_details`/`submit_response_atomically`: byte-for-byte identical shape — `anon`/`authenticated` get only structural privileges (no SELECT/INSERT/UPDATE/DELETE), `service_role` is the only role with real data access, and `cast_vote_atomically` is `security invoker` owned by `postgres`, matching every other atomic function. **Conclusion: no RLS policies for `voting_candidates`/`votes`.** This repository's established, existing security model enforces authorization entirely server-side (service-role-only access + explicit token verification inside each `security invoker` function) — RLS plays no role anywhere in this schema, and adding it now for the two new tables would be inconsistent with that precedent, not an improvement.
