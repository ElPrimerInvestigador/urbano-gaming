# Slice 009 — Engine Selection + PARTICIPANTS Voting: Implementation and Validation Record

**Status: implemented, locally validated, including mobile verification, and accepted as a strong local implementation candidate. Not yet staged, not yet committed, not yet founder-accepted.** This record documents the local implementation candidate only. No production migration, no deployment, no push, no commit, no staging has occurred. Two final-gate items (mobile host-selector verification; `.claude/launch.json` scope reconciliation) have both been closed — see "Mobile verification" below and the `.claude/launch.json` note in "Local Validation" item 4. `.claude/launch.json` carries no diff in the current working tree.

## Objective (as accepted through two founder-directed design-review rounds)

Replace the three previously-independent, only-partly-mutually-exclusive `startSession` parameters (`promptText` / `preparedQuestionId` / `votingCandidateSource`) with one discriminated, structurally-unambiguous `StartTurnConfig`; add a unified host "Choose Turn Type" selector; add `PARTICIPANTS` as a third Voting Candidate source (the session's own roster becomes the Candidate list); add structured Candidate→participant attribution and the self-vote prohibition it makes possible; and fix a **pre-existing** manual-Award-control defect, live since Slice 007 first introduced Voting (Voting's reveal has incorrectly shown the Open-Response-only manual Award button in every production build since then — `canAward`'s condition excluded only `MULTIPLE_CHOICE`, never explicitly included `OPEN_RESPONSE`, so Voting fell through to "awardable" by omission). Explicitly out of scope: Slice 010 (Voting scoring), Prediction/Golazo, Virtual Table/Private Hand implementation, canonical URBANO auth, any new Level 33 mode.

## Accepted Capability Boundary (10 items)

1. Unified host Turn Type selector (Open Response / Trivia / Voting) replacing the previous default-plus-toggle pair and the separately always-on Voting toggle.
2. Discriminated `StartTurnConfig` (`OPEN_RESPONSE` / `MULTIPLE_CHOICE` / `VOTING`) replacing the three independent flat parameters — `AmbiguousStartSessionTargetError` becomes structurally unreachable at the domain/repository layer.
3. A temporary, explicitly-commented HTTP compatibility shim at the `start` route: accepts the new `turnConfig` shape (preferred) or reconstructs an equivalent config from the legacy flat fields (fallback), isolated entirely at the route.
4. `PARTICIPANTS` Voting Candidate source — the session's current roster, snapshotted.
5. Structured Candidate→participant attribution (`voting_candidates.participant_id`).
6. Attribution stays host/server-internal — never projected to any participant-facing read path.
7. Self-vote prohibition, authoritative in `cast_vote_atomically`, mirrored by a domain-layer fast-path.
8. **Pre-existing** manual Award-control defect fix, not a Slice 009 architectural feature — explicit `currentEngineType === "OPEN_RESPONSE"` inclusion, replacing the implicit `!== "MULTIPLE_CHOICE"` exclusion that has incorrectly left the button visible after a Voting reveal in every build since Slice 007 introduced Voting. Slice 009 corrects it because it is a small correctness repair in a surface (`host.html`'s Voting-adjacent UI) this slice was already restructuring — it was not introduced by, and does not depend on, the new Turn Type selector architecture. After this fix, the manual Award control is exposed only for the one currently-supported adjudication path — Open Response, where the host remains the scoring-rule authority — and for no other engine.
9. Every Slice 007 Voting behavior preserved unchanged in intent (HOST_AUTHORED, SUBMISSION, tallying, placement, ranking).
10. Every Slice 008 Segment behavior preserved unchanged in intent (`NEW_SEGMENT`/`CURRENT_SEGMENT`, Best Joke composition, `segmentNumber` semantics).

## Design Decisions Incorporated

- **`StartTurnConfig`** — `{ engineType: "OPEN_RESPONSE"; promptText }` | `{ engineType: "MULTIPLE_CHOICE"; preparedQuestionId }` | `{ engineType: "VOTING"; promptText; candidateSource }`. Because it is a real TypeScript discriminated union, "both a preparedQuestionId and a candidateSource" is structurally unreachable through the domain function or either repository's typed `startSession` method — the runtime `AmbiguousStartSessionTargetError` check was **removed** from `InMemorySessionRepository.startSession` and from `startSession.ts`'s fast-path. The error class itself is **kept**: it remains reachable at the API route's legacy-shape compatibility shim (parsing untyped JSON), and as unchanged SQL-level defense-in-depth inside `start_session_atomically` (`AMBIGUOUS_START_TARGET`, present since 0033, carried forward verbatim in 0039).
- **`VotingCandidateSource` gains `{ type: "PARTICIPANTS" }`**, needing no extra input beyond the type discriminator — the session's own membership (already known from `sessionId`) is the entire source. Same `>= 2` Candidate floor as `HOST_AUTHORED`, enforced at both the domain fast-path and the SQL function.
- **`voting_candidates.participant_id`** — nullable, `ON DELETE SET NULL` (deliberately different from `submissions.participant_id`'s `ON DELETE CASCADE`) — a Candidate's `label` is an immutable presentation snapshot (established in 0031) that must survive regardless of the attributed participant's own lifecycle. Populated for `PARTICIPANTS` (the participant IS the candidate) and `SUBMISSION` (the submission's own author); `NULL` for `HOST_AUTHORED`. Indexed proactively (`voting_candidates_participant_id_idx`) — Postgres never auto-indexes a FK's referencing side, the same lesson already recorded against `segments`/`interaction_instances` in Slice 008.
- **Duplicate participant display names are structurally impossible today** — confirmed by direct inspection of `0003_create_participants.sql`'s `participants_session_display_name_unique` index over `(session_id, normalized_display_name)`. No disambiguation logic was added for PARTICIPANTS Candidate labels; none is needed.
- **Self-vote prohibition** is authoritative inside `cast_vote_atomically` (extends its existing candidate-ownership `SELECT` to also fetch `participant_id`, rejects when it equals the voting participant's own id), mirrored by an identical, non-authoritative fast-path in `castVote.ts`. Self-vote is prohibited **only where structured attribution exists** — `PARTICIPANTS` and `SUBMISSION` Candidates carry a real `participant_id` and are subject to the check; `HOST_AUTHORED` Candidates carry `participant_id = null` by construction, so the check is a guaranteed no-op for them (`null = p_participant_id` is never true in SQL's three-valued logic), not a separately-coded exception. **This is founder-authorized and not configurable in Slice 009** — there is no session- or Experience-level setting that permits self-voting; the rule applies unconditionally wherever attribution exists.
- **Candidate Source and Segment Target are fully orthogonal.** `SUBMISSION` + `CURRENT_SEGMENT` (the Best Joke UI flow) remains a UI-layer choice, not a domain coupling — proven directly by a new test asserting `SUBMISSION` + `NEW_SEGMENT` (segment target omitted) is accepted and starts a genuinely new Turn.
- **Off-phone activity representation — corrected scope, preserved precisely.** An earlier, overgeneralized design-review conclusion ("the host's spoken framing is real-world facilitation the app doesn't need to model as a data object") was explicitly rejected during design review as too broad. What this slice actually establishes is narrow: `PARTICIPANTS`-sourced Voting can be a Segment's sole Interaction Instance, requiring no additional runtime object beyond the existing roster. It does **not** prove, and this record does not claim, that off-phone activity in general needs no runtime representation — that remains genuinely open and unresolved, not disproven, and should not be cited as a validated architectural precedent in future work. A richer off-phone activity phase may eventually require software representation for instructions, timers, authority, roles, transitions, and private/public state — none of that is designed or implemented here, and none of it is resolved by this slice.

## Data Model

```
voting_candidates(..., participant_id)   -- new nullable column, ON DELETE SET NULL, FK to participants
```
No new tables. No `voting_candidates.session_id` column and no composite FK were added — unlike `votes`' composite FK to `voting_candidates` (0032), `participant_id` here is never client-supplied; it is always derived server-side, inside `start_session_atomically`, from a `participants` query already scoped to `p_session_id`.
