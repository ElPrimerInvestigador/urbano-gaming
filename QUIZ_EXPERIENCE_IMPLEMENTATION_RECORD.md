# Quiz Experience — Implementation Record

## Objective (as accepted)

Founder playtest experience surfaced a distinct need alongside Trivia: a self-paced, time-boxed question set where each participant progresses independently rather than waiting on host-paced "Next Question" advancement. A prior, read-only design gate (not part of this record) accepted Quiz as a distinct Experience — not a new Interaction Engine — with independent per-participant progression, reveal withheld until close, and host-configurable duration. A subsequent, read-only three-seam implementation-readiness pressure test (also not part of this record) accepted: a minimal two-column `quiz_windows` table; a dedicated `submit_quiz_response_atomically` function (not a generalization of the existing `submit_response_atomically`); and pre-creation of all N Interaction Instances at Quiz start (never lazily).

This record covers the accepted design's *implementation*: the `quiz_windows` schema, three new dedicated atomic SQL functions, the domain/repository/API layers around them, an additive `currentQuiz` read-model branch, host and participant UI, and local validation (behavioral tests, local-Postgres contract tests, and a real browser operational simulation including mobile).

## Accepted runtime composition

```
Session → Segment (= one Quiz) → quiz_windows (closes_at, closed_at) → N Multiple Choice Interaction Instances
```

At Start Quiz: one new Segment, one `quiz_windows` row, and all N Multiple Choice Interaction Instances (one per unconsumed prepared question) are created atomically, all beginning `PROMPT_ACTIVE`, all belonging to the same Segment. No new Interaction Engine was introduced — Quiz's internal Engine is `MULTIPLE_CHOICE`, identical to Trivia's; Quiz is an Experience/orchestration distinction only, expressed entirely through dedicated commands and a dedicated read-model branch, never by changing the Engine.

## Why dedicated commands, not generalized existing ones

Zero lines of `start_session_atomically`, `submit_response_atomically`, `close_submissions_atomically`, `reveal_results_atomically`, or `cast_vote_atomically` were changed. Quiz gets three new, entirely separate atomic SQL functions and three new domain functions. This was a deliberate regression-avoidance choice, not an oversight: since Trivia's own Interaction Instances share the same `MULTIPLE_CHOICE` engine type Quiz uses, any shared code path between the two would risk exactly the kind of cross-contamination this implementation in fact turned up once (see Defects below) — by keeping the write paths fully separate, that contamination was confined to the read/UI layer, where it was caught and fixed, rather than being able to reach the database layer at all.

## Files changed

**Schema (new migrations, `0041`–`0044`; no historical migration rewritten):**
- `supabase/migrations/0041_create_quiz_windows.sql` — `quiz_windows(segment_id uuid primary key references segments(segment_id) on delete cascade, closes_at timestamptz not null, closed_at timestamptz)`. No `opens_at` (derivable from `segments.created_at`), no `duration_seconds`, no `closed_by`, no status/progress/cursor columns — the minimum accepted state only.
- `supabase/migrations/0042_create_start_quiz_atomically.sql` — `start_quiz_atomically(p_session_id, p_host_token, p_duration_seconds)`. One transaction: authenticates the host token, locks the session row, verifies `LOBBY_LOCKED` and no un-revealed current interaction, validates duration (30–3600s), requires a non-empty unconsumed prepared-question set (`EMPTY_QUIZ_QUESTION_SET` otherwise, checked before any Segment/window is created), allocates a new Segment, computes `closes_at := now() + make_interval(secs => p_duration_seconds)` from database time, inserts the `quiz_windows` row, then loops over every unconsumed prepared question (row-locked `for update`) creating a prompt + `PROMPT_ACTIVE` `MULTIPLE_CHOICE` Interaction Instance + `multiple_choice_details` for each, marking it consumed, and emits one `QUIZ_STARTED` event.
- `supabase/migrations/0043_create_submit_quiz_response_atomically.sql` — `submit_quiz_response_atomically(p_session_id, p_participant_id, p_participant_token, p_interaction_instance_id, p_selected_option_index)`. Validates, in order: participant token belongs to participant and session; target Interaction Instance belongs to the session and is `engine_type = 'MULTIPLE_CHOICE'` (else `QUIZ_INSTANCE_NOT_FOUND`); a `quiz_windows` row exists for that instance's Segment (else `QUIZ_INSTANCE_NOT_FOUND`); instance is `PROMPT_ACTIVE` and `closed_at is null and now() < closes_at` (else `QUIZ_CLOSED` — authoritative, time-based, never client time); option index is in bounds (else `INVALID_OPTION_SELECTION`). Then upserts into `submissions` on `(interaction_instance_id, participant_id)` conflict (revision remains possible while open) and emits `QUIZ_RESPONSE_SUBMITTED`.
- `supabase/migrations/0044_create_close_quiz_atomically.sql` — `close_quiz_atomically(p_session_id, p_segment_id, p_caller_token)`. Locks the `quiz_windows` row; if already closed, returns `already_closed := true` immediately with zero further writes (idempotent replay). Otherwise resolves whether `p_caller_token` is the host (always allowed) or a participant (allowed only once `now() >= closes_at`, else `QUIZ_EXPIRY_NOT_REACHED`) or neither (`QUIZ_ACCESS_DENIED`); sets `closed_at = now()`; inserts `point_awards` via one `INSERT ... SELECT` across every Interaction Instance in the Segment, keyed by `md5('quiz-auto:'||instance||':'||participant)::uuid` (mirroring the existing `mc-auto:` idempotency-key pattern from `reveal_results_atomically`) with `on conflict do nothing`; transitions every Interaction Instance in the Segment to `RESULT_REVEAL` together; emits `QUIZ_CLOSED`.

- `lib/session/closeQuiz.ts` — thin pass-through to `repo.closeQuiz`, maps to `CloseQuizResult`.

- `lib/session/db/inMemorySessionRepository.ts` — full in-memory implementation mirroring each SQL function's validation order exactly, plus a `_allQuizWindows()` test helper.
- `lib/session/db/supabaseSessionRepository.ts` — `rpc()`-based implementation with `P0001` error-tag translation to the matching error class for every tag the SQL functions raise.

**Read model (additive only):**
- `lib/session/types.ts` — `QuizQuestionSummary`, `QuizParticipantProgressSummary`, `QuizSummary`, `StartQuizResult`, `SubmitQuizResponseResult`, `CloseQuizResult`; `currentQuiz: QuizSummary | null` added to `GetSessionResult`; seven new error classes (`InvalidQuizDurationError`, `EmptyQuizQuestionSetError`, `QuizInstanceNotFoundError`, `QuizClosedError`, `QuizNotFoundError`, `QuizAccessDeniedError`, `QuizExpiryNotReachedError`).
- `lib/session/getSession.ts` — an entirely new, additive code path: resolves `getQuizWindowForSegment(currentSegmentId)` and, only when a window exists, builds `currentQuiz` from the Segment's Multiple Choice instances, each instance's prompt/details/submissions, and — critically — computes `correctOptionIndex`/`isCorrect` as `null` server-side whenever `!closed`. One pre-existing field's *value* is deliberately overridden when a Quiz is active: the legacy `submissions` field (populated by unrelated, pre-Quiz logic whenever `currentInteraction.state === "RESULT_REVEAL"`) is unconditionally forced to `null` whenever `currentQuiz` is non-null — see Defect 2 below, this is the actual server-side fix for that leak, not merely a UI guard. No other pre-existing field's meaning changed.

**API routes (new, thin pass-through, matching the existing route pattern exactly):**

**Host UI (`public/host.html`):** a `Quiz` Turn Type option alongside Open Response/Trivia/Voting; a duration input (default 120s, 30–3600 bounds) and prepared-question-count hint; a `quizCard` (time remaining, per-participant progress, `Close Quiz`); a `quizFinalResultsBanner`; `closeQuizIfDue()` client-side expiry detector; and guards added to five pre-existing rendering functions (`resolvePrimaryAction`, `renderInteractionLabel`, `renderProgress`, `renderPrompt`, plus the Trivia auto-continue branch itself — see Defects) so Quiz's own Multiple Choice Interaction Instances are never misread by logic written for Trivia's.

**Participant UI (`public/participant.html`):** a distinct `quizCard` rendering branch (time remaining, `Question X of N`, prompt/options, `Next`/`Finish`, waiting message, Final Results) that participant.html's existing single-current-prompt renderer never runs alongside; forward-only local navigation (`quizLocalQuestionIndex`) reseeded from server-derived `myProgress.answered` whenever `currentQuiz.segmentId` changes; `selectQuizOption`, `quizAdvance`, `closeQuizIfDue()`; and guards added to three pre-existing rendering functions (`renderPrompt`, `renderResults`, `renderProgress`, `renderOwnCorrectnessBanner`) — one of which was a genuine privacy leak, see Defects.

**Tests:**
- `__tests__/quiz.test.ts` (new, 27 tests) — Start composition/validation/concurrency; independent progression; submission authority; privacy; Close Quiz (manual/expiry/concurrent/idempotent/scoring); reconnect.
- `__tests__/quizSupabaseRepository.contract.test.ts` (new, 9 tests) — the same seams verified live against local Postgres.

## `quiz_windows` schema (exact, as implemented)

```sql
create table if not exists quiz_windows (
  segment_id uuid primary key references segments(segment_id) on delete cascade,
  closes_at timestamptz not null,
  closed_at timestamptz
);
```

Authoritative open condition, used identically in `submit_quiz_response_atomically` and mirrored in the read model: `closed_at is null and now() < closes_at`. Client time is never authoritative anywhere in the write path — `closes_at` itself is computed once, server-side, at Start Quiz.

## Independent participant progression

No per-participant cursor or position column exists anywhere. `myProgress`/`participantProgress`/each question's `answered` flag are computed live in `getSession.ts` from the Quiz Segment's Interaction Instances joined against that participant's own `submissions` rows — nothing is written to record "where" a participant is. This was proven both in unit tests (three participants simultaneously at N/N, partial, and 0/N) and live in the browser simulation below (`get_page_text` against the host tab mid-Quiz: "Alex 3/3, Jordan 2/3, Sam 0/3", all valid at the same instant, no participant blocked by another).

## Privacy / reveal boundary

`correctOptionIndex` and `isCorrect` are computed as `null` inside `getSession.ts` itself whenever the Quiz is not yet closed — the server never transmits the data pre-close, this is not a client-side hide. Verified three ways: unit tests asserting the raw `GetSessionResult` payload; a direct live authenticated `GET_SESSION` fetch as an open-Quiz participant during the browser simulation (showed `correctOptionIndex: null, isCorrect: null` for all questions, including already-answered ones); and, after close, that only each participant's own `currentQuiz.questions` and the pre-existing aggregate `standings` are exposed — never another participant's individual answers (see the leak found and fixed under Defects).

**Permanent privacy invariant (stated explicitly, not merely implied by a test).** At every point in a Quiz's lifecycle — before close and after close alike — Participant A must never receive Participant B's raw per-question selected answer, and Participant B must never receive Participant A's, through any field of `GetSessionResult`, to any caller (participant or host). Authorized aggregate results (`score`, `standings`, rank-equivalent data) remain visible as designed; raw per-question answer content belonging to another participant does not, at any time. This is now enforced in `getSession.ts` at two independent points: `currentQuiz.questions[].correctOptionIndex`/`isCorrect` stay `null` pre-close (Quiz's own dedicated field), and the legacy `submissions` field is unconditionally suppressed to `null` whenever `currentQuiz` is active, closed or not (the boundary that actually leaked — see Defect 2). Both are covered by permanent automated regression tests (see Tests below), not left as a one-time fix.

## Timer and deadline behavior

`closesAt` is returned by Start Quiz and re-derived on every `getSession` call; both `host.html` and `participant.html` render a client-side countdown (`setInterval`, display only) from it. Submission authority never depends on the client clock — `submit_quiz_response_atomically` rejects with `QuizClosedError` once `now() >= closes_at` regardless of what the client believes the remaining time to be. When a client's timer reaches zero, `closeQuizIfDue()` (present in both host.html and participant.html) calls the same `Close Quiz` endpoint; safety comes from `close_quiz_atomically`'s idempotency guard (any number of near-simultaneous callers converge on exactly one finalization), not from any assumption that exactly one browser stays alive at the deadline. No background scheduler/cron was introduced — this lightweight polling-trigger strategy was judged sufficient for the proving case, consistent with the accepted design.

## Scoring

Reuses the existing Multiple Choice scoring mechanism unchanged: `close_quiz_atomically` writes `point_awards` rows (correct → the question's configured points; wrong or unanswered → no row, i.e. zero) using the same idempotency-key pattern Trivia's own `reveal_results_atomically` already established. No second scoring ledger, no Lifestyle Points/Reward Economy conversion, and no new Game Outcome/champion abstraction were introduced — the existing session `standings` serve as the Quiz's final result, exactly as for Trivia.

## Reconnect behavior

Nothing participant-progress-related is read from `localStorage`. A fresh `getSession` call after reconnect re-derives `currentQuiz` (including `myProgress`) purely from server-side Interaction Instance + submission state; the participant's local `quizLocalQuestionIndex` is only ever (re)seeded from that server-derived `myProgress.answered`, never trusted from a prior session. Covered directly in `quiz.test.ts`'s reconnect tests (fresh `getSession` calls after simulated disconnect reproduce the same progress a live session would show).

## Defects found and fixed during this implementation

**1. Segment-reuse regression at the Trivia/Quiz boundary (found during mobile validation, fixed before sign-off).** `host.html`'s pre-existing "Trivia auto-continue" branch (`resolvePrimaryAction()`) checked only `currentEngineType === "MULTIPLE_CHOICE" && interactionLifecycleState === "RESULT_REVEAL" && hasNextQuestion` to decide whether to silently continue as "Next Question" in the current Segment. Since a just-closed Quiz's last Interaction Instance is also `RESULT_REVEAL` / `MULTIPLE_CHOICE`, a host who closed a Quiz and then added more prepared questions to the queue would have the session auto-continue as a Trivia "Next Question" — reusing the Quiz's own Segment (which already carries a `quiz_windows` row) for unrelated Trivia content, and causing `currentQuiz` to keep resolving (stale) for that Segment. A `quizJustClosed` guard already existed for the adjacent `triviaJustFinished` banner logic but had not been applied to this earlier branch. Fixed by computing `quizJustClosed` before, and adding it to, the auto-continue condition. Reproduced directly: before the fix, starting a Quiz, closing it, adding a new prepared question, and clicking the (mislabelled) primary action produced a `POST /start` request that landed in the Quiz's own Segment (`segmentNumber` unchanged, `currentQuiz` still resolving for the closed Quiz). After the fix, the identical sequence correctly shows "Choose Turn Type"; a subsequent Trivia start opens a **new** Segment (`segmentNumber` incremented) with `currentQuiz: null`, confirmed via a live authenticated `GET_SESSION` call during the browser simulation.
**Root cause**: a client-side (host.html) decision-logic gap — the domain layer's `startSession` already defaults to `NEW_SEGMENT` and was never itself at fault; the bug was that the client sometimes called the wrong composed action entirely.
**Permanent regression coverage**: this repository has no DOM/render test harness (no jsdom or `@testing-library` dependency exists in `package.json`), so the client-side decision function itself cannot be unit-tested without introducing a new testing framework — judged disproportionate for one conditional. Instead, `__tests__/quiz.test.ts`'s new **"Quiz/Trivia Segment isolation regression"** test proves the structural invariant a correctly-behaving client depends on: it reproduces the exact triggering state (Quiz closed, a prepared question left unconsumed) and asserts, at the Segment-identity level — not text/DOM — that `startSession`'s default `NEW_SEGMENT` path (the domain call "Choose Turn Type → Start Trivia" must invoke) always produces `triviaInstance.segmentId !== quizResult.segmentId`, `repo._allSegments()` growing to 2, and `getSession()`'s `currentQuiz` resolving to `null` for the new state. This does not test host.html's JS directly, but it does guarantee the domain-layer contract that JS depends on can never silently regress back into producing shared Segments.

**2. Cross-participant privacy leak — deeper than first documented; a real server-side leak, not only a rendering bug (found live in the browser simulation; the full server-side root cause found and fixed during this final acceptance gate).** `participant.html`'s pre-existing `renderResults()` — written for Open Response's results card — populates from `GET_SESSION`'s existing (non-Quiz-specific) `submissions` field. Once a Quiz closed, this caused another participant's raw answer (observed live as "Alex ✓ A" rendered on Sam's own screen) to appear on a participant's own view — a direct violation of the founder's explicit no-cross-participant-visibility requirement. The first fix applied (during browser simulation) only guarded the client rendering (`if (currentQuiz) { card.style.display = "none"; return; }`), which stopped the on-screen display but **did not stop the underlying data from being transmitted**: `lib/session/getSession.ts`'s `submissions` field is populated for *every* caller (host and every participant alike) whenever `currentInteraction.state === "RESULT_REVEAL"` — a rule written for Trivia/Open Response/Voting, where showing everyone's answers post-reveal is normal, intended UX, long before Quiz existed. Since Close Quiz transitions every Quiz Interaction Instance (including the last-created one, which is `currentInteraction`) to `RESULT_REVEAL` together, this field kept carrying every participant's raw answer to the Quiz's last question over the actual network response to every caller, independent of any client-side rendering. **This was caught only during this final acceptance-gate review**, by re-reading `getSession.ts` end-to-end rather than trusting the earlier client-side fix was sufficient — the automated privacy tests at the time only exercised the new, already-correctly-gated `currentQuiz` field, and the live screenshot verification only proved the *symptom* (nothing rendered) was gone, not that the *data* was gone.
**Fix**: `getSession.ts` now unconditionally sets `submissions = null` whenever `currentQuiz` is non-null (i.e. whenever the current interaction belongs to any Quiz Segment, open or closed) — the actual read-model boundary, not a display guard. Quiz has its own dedicated, correctly-scoped equivalent (`currentQuiz.questions` / `currentQuiz.participantProgress`), so the legacy field is now fully suppressed for Quiz rather than merely hidden.
**Permanent regression coverage**: `__tests__/quiz.test.ts`'s new **"Privacy — cross-participant answer isolation (legacy `submissions` field regression)"** test targets this exact boundary directly — two participants answer the Quiz's last question with deliberately different options, and the raw `GetSessionResult.submissions` field (not `currentQuiz`) is asserted `null` for both participants and the host, both before close (naturally null, asserted explicitly rather than assumed) and after close (the actual state that leaked). Standings remain asserted as visible and correctly computed, confirming the fix suppresses only raw answer content, not authorized aggregate results.

**3. Missing CSS collapse rule (found live, fixed before sign-off).** `#quizStartForm.collapsed { display: none; }` was omitted when the Quiz Turn Type form was added, so the duration input remained visible even while `LOBBY_OPEN` (the same defect class this codebase had already hit once before for `#votingStartForm`). Fixed by adding the missing rule.
**Regression coverage**: no DOM/render test harness exists in this repository (see Defect 1's reasoning), so a real rendering assertion isn't available without introducing a new testing framework for one cosmetic rule — judged disproportionate. A focused static assertion the existing plain-Node Vitest setup already supports was added instead: `__tests__/quiz.test.ts`'s new **"host.html Quiz form collapse CSS regression"** test reads the actual shipped `public/host.html` source and asserts both halves of the fix are present together (the JS still toggles the `collapsed` class, and a matching CSS rule still collapses it) — a future edit reintroducing only one half fails this test.

All three fixes, and their permanent automated regression coverage, are included in the file diffs and test/verification totals below; no defect was left outstanding at sign-off.
